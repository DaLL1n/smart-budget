# **КОНСТИТУЦИЯ ПРОЕКТА: СЕРВИС МОНИТОРИНГА ПРОДУКТОВОГО БЮДЖЕТА**

## **1\. Технологический стек и архитектура (Tech Stack)**

При написании и изменении кода агент обязан использовать исключительно следующие технологии и актуальные версии:

* **Фронтенд-ядро:** React 19.0.1, Vite 6.2.3, TypeScript (\~5.8.2).  
* **Архитектурная методология:** Feature-Sliced Design (FSD) — разделение на слои app/, pages/, widgets/, features/, entities/, shared/.  
* **Управление данными и кэширование:** TanStack Query (@tanstack/react-query v5) с персистентным оффлайн-кэшем через @tanstack/react-query-persist-client и idb-keyval (IndexedDB).  
* **Маршрутизация:** TanStack Router (@tanstack/react-router v1) с типобезопасными маршрутами и централизованным defaultErrorComponent.  
* **Реактивное локальное состояние:** TanStack Store (@tanstack/store, @tanstack/react-store).  
* **Контроль асинхронности, дебаунс и rate limiting:** TanStack Pacer (@tanstack/react-pacer, @tanstack/pacer) — дебаунс поиска магазинов и продуктов, батчинг сетевых запросов и троттлинг запросов к AI-ассистенту.  
* **Визуализация и графики:** TanStack Charts (@tanstack/charts).  
* **Таблицы и списки покупок:** TanStack Table (@tanstack/react-table v9) — управление табличными данными, умными списками продуктов по магазинам, сортировкой, фильтрацией и группировкой.  
* **Стилизация:** Tailwind CSS v4.1.14 (прямая нативная интеграция через плагин @tailwindcss/vite).  
* **Анимации:** Motion v12.23.24 (motion/react).  
* **Иконки:** Lucide React (^0.546.0).  
* **Отказоустойчивость:** Двухуровневый ErrorBoundary (глобальный в app/ \+ изолированные предохранители виджетов QueryErrorBoundary) с интеграцией QueryErrorResetBoundary и автоматической защитой от утечек информации в продакшене (import.meta.env.DEV).  
* **База данных и облачный бэкенд:**  
  * **Supabase** (@supabase/supabase-js ^2.113.0) — единая полнофункциональная база данных (PostgreSQL) и аутентификация пользователей (Supabase Auth). Все данные пользователей (public.users), семейных пространств (public.families) и расходов (public.expenses) хранятся и управляются строго через Supabase.  
* **Сетевой слой, переменные окружения и валидация:** axios (^1.20.0) для HTTP-интеграций, .env (VITE\_SUPABASE\_URL, VITE\_SUPABASE\_ANON\_KEY), zod (^4.5.4) для строгой runtime-валидации DTO и контрактов.

## **2\. Локальный запуск и окружение (Dev Environment)**

* **Порт фронтенда (Vite):** Запуск строго на порту 3000 (vite \--port=3000 \--host=0.0.0.0).  
* **Скрипты:**  
  * npm run dev — запуск Vite-сервера разработки на порту 3000\.  
  * npm run build — сборка оптимизированного продакшен-бандла (dist).  
  * npm run clean — очистка папки сборки (dist).  
  * npm run lint — проверка статической типизации (tsc \--noEmit).

## **3\. Спецификации и ограничения Gemini 3.8 Flash (Model Guardrails)**

Все агенты и генерируемые промпты обязаны учитывать технические параметры модели Gemini 3.8 Flash:

1. **Контроль мышления (Thinking Control):**  
   * Для архитектурного анализа, дебаггинга и оптимизации промптов использовать строго thinking\_level \= "medium" или thinking\_level \= "high".  
   * Режим minimal моделью не поддерживается.  
2. **Запрет устаревших параметров:**  
   * Полное исключение параметров temperature, top\_p, top\_k, candidate\_count, frequency\_penalty, presence\_penalty. Управление детерминизмом осуществляется исключительно через thinking\_level.  
3. **Полный запрет LaTeX-разметки:**  
   * Категорически запрещено использовать теги \\sum, \\le, \\ge, \\mathcal{O}, $, $$ в коде, markdown-документах и таблицах.  
   * Сложность операций записывать строго в ASCII-нотации: O(1), O(N), O(log N). Сравнения писать как \<=, \>=, \!=.  
4. **Форматирование и парсинг:**  
   * Смысловые блоки, системные директивы и списки разделять двойным переносом строки (\\n\\n).  
   * Исключить генерацию префиксов и пустых prefilled-ответов.

## **5\. Сквозной конвейер выполнения задач (Sequential Pipeline)**

Любая входящая задача пользователя проходит строгий детерминированный маршрут. **Прямое внесение правок в кодовую базу из сырого запроса пользователя категорически запрещено.**

\[Входящий запрос пользователя\]  
               │  
               ▼  
   \[Шаг 0: Prompt Architect\]  
   (Навык: prompt-optimizer)  
               │  
               ▼  
   \[Артефакт: TASK\_SPEC.md\] ◄─────────────────┐ (Контракт передачи задачи)  
               │                               │  
               ▼                               │  
   \[Шаг 1: Feature Developer\]                  │  
   (Навык: feature-developer)                  │  
               │                               │  
               ▼ \[handoff.md: SUCCESS\]         │  
   \[Шаг 2: Logic Tester\]                       │  
   (Навык: feature-tester) ───\[ОШИБКА КОДА\]────┤ (Loopback-контракт)  
               │                               │  
               ▼ \[test-report.md: SUCCESS\]     │  
   \[Шаг 3: UI/UX Tester\]                       │  
   (Навык: browser-ui-tester) ─\[ОШИБКА UI\]─────┘  
               │  
               ▼ \[ui-audit-report.md: SUCCESS\]  
        \[ФИНАЛ РЕАЛИЗАЦИИ\]

### **Регламент шагов конвейера:**

* **Шаг 0 (Калибровка задачи):** Агент-Оптимизатор принимает сырой промпт, форматирует его по 4-компонентной схеме Google (Persona, Task, Context, Format) с учетом лимитов Gemini 3.8 Flash, сохраняет артефакт в .agent/tasks/TASK\_SPEC.md и передает эстафету агенту feature-developer.  
* **Шаг 1 (Разработка):** Разработчик считывает .agent/tasks/TASK\_SPEC.md, применяет стек проекта (React 19, Vite, TanStack, Supabase), пишет код в изолированной ветке и генерирует отчет передачи .agent/handoff.md.  
* **Шаг 2 (Тестирование логики):** Агент feature-tester читает .agent/handoff.md, запускает проверку типов (npm run lint), выполняет автотесты логики и формирует отчет .agent/test-report.md.  
* **Шаг 3 (Визуальный аудит):** Агент browser-ui-tester поднимает сервер (npm run dev), через команду /browser проверяет отображение интерфейса на брейкпоинтах (375px, 768px, 1440px) и создает отчет .agent/ui-audit-report.md.

## **6\. Протоколы артефактов и эстафеты (Handoff Contracts)**

### **6.1. Спецификация файла задачи (.agent/tasks/TASK\_SPEC.md)**

Артефакт создается агентом prompt-optimizer и служит единственным источником правды для разработчика:

* **Раздел 1 (Persona & Role):** Четкая инженерная роль (Senior Frontend Developer / Supabase Architect).  
* **Раздел 2 (Task & Workflow):** Краткая формулировка задачи и декомпозированный список шагов реализации.  
* **Раздел 3 (Context & Guardrails):** Указание стека (React 19, FSD, TanStack, Supabase, Tailwind v4), директива thinking\_level \= "medium" / "high", полный запрет LaTeX и жесткие архитектурные ограничения проекта.  
* **Раздел 4 (Format & Definition of Done):** Чек-лист проверки: отсутствие ошибок компилятора (tsc \--noEmit), прохождение тестов логики и создание файла эстафеты .agent/handoff.md.

### **6.2. Манифест передачи состояния (.agent/handoff.md)**

Передается между разработчиком и тестировщиками со следующей обязательной структурой полей:

* source\_agent: Идентификатор передающего агента (feature-developer | feature-tester | browser-ui-tester).  
* status: Статус выполнения (SUCCESS | FAILED).  
* artifacts\_produced: Список созданных или измененных файлов проекта.  
* pending\_tasks: Задачи, оставшиеся нерешенными или требующие внимания.  
* blockers\_or\_notes: Логи терминала, предупреждения или детальное описание дефектов.

## **7\. Алгоритм циклической самокоррекции (Self-Correction Loop)**

Если на шаге логического или визуального тестирования обнаружен дефект:

1. Тестировщик останавливает текущий шаг конвейера и переводит статус в FAILED.  
2. В начало .agent/handoff.md добавляется управляющий маркер \[RE-RUN\_DEVELOPMENT\].  
3. В манифесте подробно описывается причина возврата:  
   * **Для ошибок логики:** упавшие тесты, трассировка стека и ошибки компилятора TypeScript.  
   * **Для ошибок интерфейса:** CSS-селектор проблемного блока, брейкпоинт экрана (375px / 1440px) и относительный путь к сделанному скриншоту.  
4. Контроль передается агенту feature-developer, который правит код и перезапускает цикл верификации.

## **8\. Предохранитель от бесконечного цикла (Circuit Breaker)**

* Лимит итераций самокоррекции между разработчиком и тестировщиками: **не более 3 циклов**.  
* На 4-й итерации конвейер немедленно останавливается, формируется файл .agent/failed-pipeline.md с дампом ошибок, и агент запрашивает ручное вмешательство пользователя.

## **9\. Регламент Git-воркфлоу и ограничения разработки (Constraints)**

* **Изоляция кода:** Любое изменение кода выполняется строго в изолированном рабочем дереве (Git Worktree) или отдельной feature-ветке. Прямые коммиты в ветки main и master заблокированы.  
* **Интеграционный протокол:**  
  1. Инициализация через команду /grill-me для снятия неопределенности при сложных требованиях.  
  2. Запуск конвейера через /goal для непрерывного автономного выполнения до финального статуса.  
  3. Подтверждение работы UI через встроенный браузер /browser.

## **10\. Верификация UI/UX и визуальной стабильности (Visual QA Rules)**

* **Адаптивный аудит:** Обязательная проверка страниц меню «Семья», дашборда продуктовых корзин и раздела «Аналитика» на контрольных брейкпоинтах: 375px (Mobile), 768px (Tablet), 1024px (Laptop), 1440px (Desktop).  
* **Запрещенные дефекты UI (No-Drift Check):**  
  * Появление горизонтального скролла на экранах от 375px.  
  * Смещение верстки (Layout Shifts) при переключении фильтров и маршрутов TanStack Router.  
  * Наложение полей ввода цен продуктов, кнопок добавления и ячеек TanStack Table друг на друга.  
  * Обрезание текста (Text Truncation) без явного CSS-правила многоточия.

## **11\. Продуктовые и смысловые правила интерфейса (Product UX Guardrails)**

* **Лимиты на дашборде:** В карточке бюджета под прогресс-баром обязательно выводятся два четких ориентира: «Лимит в неделю» и «Лимит в день». Запрещено дублировать остаток бюджета или писать «в среднем в день».
* **Изоляция пространств Личное / Семейное:** 
  * На дашборде (`/dashboard`) всё планирование, бюджет и рацион являются строго ЛИЧНЫМИ (1 персона), без упоминания семьи.
  * Планирование для семьи, учет предпочтений родственников и общий семейный бюджет располагаются исключительно в разделе «Семья» (`/family`).
* **Запрет формулировки «в среднем в день»:** В любых блоках планирования и бюджета использовать только четкие лимиты: «Бюджет на закупку N дней» или «Лимит в день (максимум)». Не вводить пользователя в заблуждение усредненными абстрактными цифрами.
* **Чистый бренд-нейминг функций:** Не отображать в UI технические плашки движков («Gemini», «GPT»). Функции оформляются как нативная часть сервиса («Шеф-меню и умная корзина»).
* **Принцип единого AI-агента приложения:** Пользователь никогда не вводит персональные API-ключи. Все AI-функции работают через встроенный ключ и агент самого приложения.
* **Мультиканальный ввод чеков:** AI-сканер чеков обязан поддерживать 5 источников: камера, фото из галереи, документ (PDF/файл), вставка скопированного текста и ссылка на электронный чек.
* **Обязательный интерактивный предпросмотр AI-чека:** Распознанные позиции и категории чека всегда выводятся на экран предпросмотра с детализацией по товарам и возможностью свободного редактирования перед финальным сохранением.
* **Пакетная запись чека (Batch Save):** Все распознанные категории чека сохраняются в историю покупок одним действием без повторных циклов.
